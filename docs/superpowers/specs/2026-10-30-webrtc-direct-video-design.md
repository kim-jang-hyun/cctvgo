# 영상 직접 전송(WebRTC) 설계

작성일: 2026-10-30 · 브랜치: `webrtc` · 보존 태그: `hls-v1.0` (HLS 방식 마지막 상태, 806a877)

## 1. 왜 바꾸는가

CCTVGO의 목적: 잘 보이던 카메라가 통신사 변경, IP 변경 등으로 어느 날 밖에서 안 보이게 된다. 이때 고객이 포트포워딩 같은 어려운 설정을 하지 않아도, **설치만 하면 외부 웹브라우저에서 영상을 볼 수 있게** 한다. 이것을 사업으로 연결하는 것이 목표다.

현재는 영상(HLS)까지 전부 `브라우저 → Cloudflare → 터널 → 고객 PC(localhost:8085)` 경로로 간다. 모든 고객이 운영자(김장현) 계정 하나의 Cloudflare 터널과 `cctvgo.app` 하위 주소를 쓴다. Cloudflare Free 플랜은 트래픽 요금을 청구하지 않는다. 다만 영상 전송이 약관 위반으로 판단되면 계정 제한이나 유료 서비스 전환을 요구받을 수 있고, 계정이 하나라서 그때는 모든 고객이 함께 멈춘다.

**운영자 원칙 (확정):** CCTVGO 운영에 드는 돈은 도메인 구입·갱신비 하나뿐이다. 중계 서버(VPS, TURN), Cloudflare 유료 플랜, 고객 수에 따라 늘어나는 비용은 모두 쓰지 않는다. 시험용 장비를 한 번 사는 것(예: 공유기)은 운영비가 아니다.

## 2. 목표 / 하지 않을 것 / 실패로 보는 것

**목표**
- 영상은 고객 PC에서 시청자 브라우저로 **직접**(WebRTC, UDP) 간다. 영상 데이터는 Cloudflare를 거치지 않는다.
- 고객은 설정을 하지 않는다. 유일하게 허용하는 동작은 첫 실행 때 Windows 권한 확인 창(UAC)에서 "예"를 한 번 누르는 것이다(4.5).
- 직접 연결이 안 되는 환경에서는 화면에 원인과 함께 "이 네트워크 환경에서는 외부 시청이 불가능합니다"를 분명히 안내한다.
- **연결 실패와 설치·운용 중 문제를 원인까지 기록한다.** 나중에 UPnP 같은 기능을 추가할 근거로 쓴다(4.7).
- H.265 카메라는 메인과 H.264 서브를 함께 저장하고, 브라우저에 맞는 쪽을 자동으로 고른다(4.6).
- 나중에 Cloudflare를 완전히 걷어낼 수 있도록 시그널링 부분을 분리한다. 이번 작업에서 걷어내지는 않는다.

**하지 않을 것 (이번 범위 밖)**
- Cloudflare 제거. UI, 로그인, 설정, 시그널링은 계속 Cloudflare 터널을 쓴다(트래픽이 아주 적다).
- **UPnP.** 시험 결과 UPnP 없이 LTE 직접 연결에 성공했고, 시험 환경(LG U+ 공유기)은 UPnP를 지원하지 않아 실제 확인이 불가능하다. 실제 공유기(예: ipTIME)로 확인할 수 있을 때, 그리고 실패 기록이 근거로 쌓였을 때 추가한다. 넣을 자리(모듈 경계)만 비워 둔다.
- PC 브라우저용 H.265 → H.264 변환. WebRTC 완성 후 별도 작업으로 한다. 방법은 시험으로 확인해 두었다(8절).
- 녹화, 음성, 화질 선택.
- HLS 방식을 코드에 함께 남기는 것. 필요하면 `hls-v1.0` 태그에서 가져온다.

**실패로 보는 것 (기술적으로 돌아가도 실패)**
- 영상 데이터가 어떤 경로로든 Cloudflare를 지나는 것. 연결 실패 시 Cloudflare로 대신 보내는 대체 경로도 금지다.
- 운영자에게 반복 비용이 생기는 구성(TURN, 유료 API, 유료 플랜, 로그 수집 서버 포함).
- 고객에게 설정(공유기, 방화벽, 카메라 코덱 등)을 시키는 것.
- 카메라를 추가·수정·삭제할 때 다른 카메라 영상이 끊기는 것.
- 카메라 주소 찾기가 인증 실패 예산(IP별 2회)을 넘겨 카메라 계정을 잠그는 것. 예산 완화는 금지다.
- go2rtc 관리 API가 외부(Cloudflare 터널 포함)나 LAN에서 접근 가능해지는 것(4.1 보안).

**받아들인 한계 (운영자 확정):** 모든 네트워크 환경에서 외부 시청이 되지는 않는다.

## 3. 시험으로 확인한 사실 (2026-10-30)

시험 환경: 개발 PC(i5-1334U, Intel Iris Xe, Wi-Fi, Windows 네트워크 프로필 "공용"), LG U+ 공유기 `192.168.219.1`(공인 IP 받음, **UPnP 없음**). 카메라 2대: H.264 1080p25(`/Streaming/Channels/101`), H.265 2560x1440 20fps + G711 음성(`/onvif1`, 서브 `/onvif2`도 **H.265** 640x368).

MediaMTX v1.21.3과 go2rtc v1.9.15를 같은 조건으로 시험했다. 기록: `docs/superpowers/spikes/2026-10-30-media-server-spike.md`.

- 지연: 둘 다 체감상 실시간이다(HLS는 약 10초).
- CPU/메모리(변환 없음): 둘 다 매우 낮다(<0.2%, 약 50MB).
- **LTE(LG U+ 알뜰폰) 외부 시청을 UPnP 없이 확인했다:** STUN 바깥 주소끼리 직접 연결됐다(집 공인 IP의 srflx ↔ LTE srflx). 시그널링만 임시 Cloudflare 터널을 지났다.
- 카메라 전원 차단 후 복구: 둘 다 카메라에 자동으로 재접속했다. go2rtc는 브라우저 연결을 유지했고, 시험 화면의 video가 일시정지 상태로 남아 재생 버튼이 필요했다. 우리 화면에서는 자동 재생으로 처리해야 한다.
- H.265: 아이폰(사파리 엔진)은 WebRTC로 재생된다. PC 크롬 156은 "codecs not supported"로 실패했다.
- go2rtc + 번들 FFmpeg로 H.265를 H.264로 변환하면 PC 크롬에서 재생됐다(8절).
- Windows 방화벽: 첫 실행 때 허용 창이 떴고, 허용하면 인바운드 규칙이 생겼다.

**미디어 서버 결정: go2rtc.** 근거는 H.265를 못 받는 브라우저용 변환 연동(FFmpeg)이 내장되어 있다는 점이다. 메인·서브가 모두 H.265인 카메라가 실제로 있으므로 PC 시청에 필수다. 또 기본 동작이 "보는 사람이 있을 때만 카메라에 접속"이다. MediaMTX의 장점인 녹화 내장은 나중 단계이고, FFmpeg로 따로 만들 수 있다.

## 4. 새 구조

| 무엇 | 경로 | 비고 |
|---|---|---|
| UI, 로그인, 설정, 카메라 관리 | Cloudflare 터널 (지금과 같음) | |
| 시그널링 (SDP 교환) | Cloudflare 터널 → server.js(인증) → 로컬 go2rtc | 접속당 몇 KB |
| 영상 | 고객 PC → 시청자 브라우저 직접 (WebRTC/UDP) | Cloudflare를 거치지 않음 |
| 같은 LAN에서 볼 때 | `http://LAN-IP:8085`, 영상도 LAN 직접 | |

### 4.1 go2rtc
- `go2rtc.exe`(MIT, exe 하나)를 설치 폴더에 넣는다. 버전은 개발 시점 최신 안정판으로 정한다(빌더 결정).
- **보안 (필수):**
  - go2rtc 관리 API(`/api/streams` 등)로는 스트림 추가가 가능하고, `exec:` 소스는 임의 명령 실행이 된다. 그래서 API/HTTP 포트는 반드시 `127.0.0.1`에만 연다.
  - server.js는 WebRTC 시그널링 요청만 골라 전달하고, 관리 API는 절대 전달하지 않는다.
  - 이번 범위에서 `exec`이 필요 없으면 끈다. 같은 PC의 다른 프로그램이나 브라우저(CSRF, DNS 리바인딩)가 localhost API를 악용하지 못하게 하는 방법도 빌더가 확인한다.
- 외부와 LAN에 열리는 것은 WebRTC 포트(시험값 8555, UDP와 TCP) 하나뿐이다.
- go2rtc 내부 RTSP 서버는 변환 기능에 필요하다(8절). 열더라도 `127.0.0.1`에만 연다.
- 바깥 주소: `webrtc.candidates`에 `stun:<포트>`를 두고, ICE 서버로 무료 공용 STUN(`stun:stun.l.google.com:19302` 등)만 쓴다.
- 카메라 목록의 기준은 **`cctv.txt`뿐**이다. go2rtc는 API로 스트림을 추가하면 자기 설정 파일에 써 넣는다(시험에서 확인). 그러므로 시작할 때마다 `cctv.txt`로 go2rtc 설정을 새로 만들고, 실행 중 변경은 API로 반영한다. go2rtc 설정 파일은 언제 지워져도 되는 파일로 다룬다.
- 카메라 접속 방식: TCP. 볼 때만 접속(go2rtc 기본)할지 항상 접속할지는 빌더가 정한다. 다만 첫 화면이 뜨는 시간과 카메라 동시 접속 수를 함께 고려한다.

### 4.2 기존 영상 관리(StreamManager) 대체
- FFmpeg 프로세스 관리(`run_single_stream.bat`, `processes.js`의 영상 부분, `hls` 폴더)를 go2rtc 스트림 관리로 바꾼다. FFmpeg 실행 파일은 8절의 변환 작업을 위해 패키지에 남긴다.
- 지금 StreamManager의 규칙을 그대로 지킨다.
  - stream 번호 k는 카메라 주소 기준으로 배정하고 재사용하지 않는다.
  - 다른 카메라는 건드리지 않는다.
  - 작업은 한 줄로 차례대로 실행한다.
  - 같은 주소가 여러 줄이면 앞에서부터 짝짓는다.
- go2rtc가 죽거나 응답하지 않을 때의 감시와 재시작은 cctvgo-service가 맡는다(빌더가 방법 결정).

### 4.3 시그널링
- 브라우저 → `server.js`의 인증된 API(경로 이름은 빌더 결정) → `127.0.0.1`의 go2rtc WebRTC 엔드포인트. 로그인 세션이 없으면 거절한다.
- 시그널링은 백엔드 프록시 하나와 프론트엔드 연결 함수 하나로 분리한다. 나중에 Cloudflare 대신 다른 수단을 쓸 때 이 두 곳만 바꾸면 되게 한다.
- `/api/get-channel-list`는 HLS 주소 대신 카메라별 스트림 식별자를 준다. H.265 카메라는 원본과 대체 스트림(서브 또는 나중의 변환본)을 함께 준다.

### 4.4 NAT 통과
- STUN만 쓴다(무료 공용). **TURN 없음, UPnP 없음(이번 범위).**
- UPnP를 나중에 추가할 수 있도록, "외부에서 닿을 수 있는 추가 주소 후보를 go2rtc에 알려 주는" 자리를 한 곳에 모아 둔다.

### 4.5 Windows 방화벽
- go2rtc WebRTC 포트에 대한 인바운드 허용 규칙이 필요하다. 시험에서 허용 창을 누른 뒤 LAN·외부 연결이 정상이었다.
- **운영자 결정:** 첫 실행 때 UAC "예" 한 번은 허용한다. `cctvgo.bat`이 규칙이 없을 때만 관리자 권한으로 규칙을 추가한다. 규칙이 있으면 다시 묻지 않는다.
- 규칙은 이 설치 폴더의 `go2rtc.exe`만 대상으로 하고, 다른 폴더의 CCTVGO와 섞이지 않게 한다.
- 고객이 "아니요"를 누르거나 실패해도 서비스는 정상 실행된다. 그 사실은 4.7에 따라 기록한다.

### 4.6 화면 (LiveCctv.vue)
- hls.js를 WebRTC 재생으로 바꾼다. 데스크톱 그리드, 드래그 교체, 모바일 1채널과 탭 선택 등 기존 화면 동작은 유지한다.
- 연결 상태를 표시한다: 연결 중 / 재생 중 / 실패(원인).
- 실패 판정 시간은 빌더가 정한다.
- 안내 문구는 원인을 구분한다.
  - 네트워크로 연결 안 됨: "이 네트워크 환경에서는 외부 시청이 불가능합니다"
  - 코덱 미지원: "이 브라우저에서는 이 카메라 영상(H.265)을 재생할 수 없습니다"
  - 카메라 응답 없음
- **자동 복구:** 카메라 재접속, 연결 끊김, video 일시정지가 생기면 사용자 조작 없이 다시 재생한다. 카메라 목록이 바뀌면 바뀐 칸만 다시 연결한다.
- **코덱 선택:** 브라우저가 H.265를 받을 수 있는지(`RTCRtpReceiver.getCapabilities` 등) 확인한다. 받을 수 있으면 원본을, 아니면 대체 스트림(H.264 서브, 나중에는 변환본)을 요청한다. 대체 스트림이 없으면 코덱 미지원 안내를 띄운다.
  - 시험에서 원본과 변환본을 go2rtc의 한 스트림 이름에 묶었더니 원본의 음성만 잡히고 변환이 시작되지 않아 검은 화면이 됐다. 그래서 **원본과 대체는 별도 스트림 이름**으로 두고 화면이 고른다.

### 4.7 실패·운용 기록 (운영자 요청: UPnP 등 기능 추가의 근거)
목표는 고객이 문의할 때 "왜 안 됐는지"를 사실로 남기는 것이다. **로그 수집 서버는 두지 않는다**(비용 원칙). 기록은 고객 PC의 `logs` 폴더에 남긴다. 설정 화면에 기존 카메라 찾기의 진단 정보처럼 **"진단 정보 복사"**를 두어, 고객이 문의할 때 붙여 보내게 한다.

기록할 것:
- **시청 연결마다** (서버 측, 시그널링과 go2rtc 정보로)
  - 시각, 카메라 번호, 결과(성공/실패/중간 끊김)
  - 실패 단계(시그널링 / ICE / 코덱 / 카메라)
  - 선택된 후보 종류(host/srflx/prflx)와 연결에 걸린 시간
  - 브라우저 종류
- **브라우저 측 보고**: 화면이 실패했을 때 원인과 브라우저가 수집한 후보 종류 요약을 서버에 보낸다. 서버는 이것을 같은 로그에 남긴다.
- **시작할 때 환경 점검**
  - 방화벽 규칙 유무, Windows 네트워크 프로필(공용/개인)
  - STUN으로 얻은 바깥 주소를 얻었는지, 공인 IP인지 사설·CGNAT 대역(100.64.0.0/10 등)인지
  - 이중 공유기 의심 여부(기본 게이트웨이 뒤에 또 사설망이 있는지 등, 빌더가 판단 가능한 범위)
  - UPnP 공유기 응답 여부(**조회만**, 포트는 열지 않음): 이것이 UPnP 추가를 판단하는 직접 근거가 된다.
- **운용 중**: go2rtc 비정상 종료와 재시작, 카메라 연결 끊김과 복구, 방화벽 규칙 추가 실패.
- **개인정보:** 시청자 IP는 전부 남기지 않는다(예: 앞 두 자리만). 카메라 비밀번호는 절대 남기지 않는다(지금 규칙과 같음).
- 로그 보관: 지금처럼 오래된 로그는 7일 뒤 삭제한다. 다만 연결 통계 요약(성공·실패 횟수, 원인별)은 더 오래 남길 수 있게 빌더가 정한다.

### 4.8 카메라 주소 찾기: 코덱 확인과 서브 스트림
- DESCRIBE 응답 SDP의 비디오 `a=rtpmap`에서 코덱(H264/H265 등)을 읽어 후보에 붙인다.
- 저장 규칙:
  - 메인(첫 번째 성공 후보)이 H.264이면 메인만 저장한다(지금과 같음).
  - 메인이 H.265이면 서브 스트림을 찾아서, 있으면 **함께 저장**한다. 서브가 H.264이면 PC용 대체로 쓰고, 서브도 H.265이면 저장은 하되 대체로 쓰지 않는다(8절 변환 작업 때 쓰임).
- ONVIF 경로는 이미 최대 4개 프로파일을 검증하므로 코드만 보고 고른다.
- 경로 후보 탐색에서 처음 성공한 경로가 H.265이면 같은 제조사의 서브 경로(예: `/Streaming/Channels/102`, `subtype=1`, `_sub`, `/stream2`, `/onvif2`, `profile2`)를 추가로 확인한다. 인증 실패 예산을 넘기지 않는다. 계정은 이미 맞았으므로 보통 404만 나오지만, 401이 나오면 기존 규칙대로 센다.
- 사용자에게 보이는 선택 화면은 늘리지 않는다. 카메라 하나로 보인다.
- `cctv.txt` 형식을 늘려 카메라당 서브 주소를 하나 더 적을 수 있게 한다. **기존 파일은 그대로 읽혀야 한다.** 카메라 편집 화면도 서브 주소를 보존해야 한다(지우지 않음). 형식은 빌더가 정한다.
- 이미 등록된 카메라의 주소는 바꾸지 않는다.

### 4.9 실행과 패키징
- MediaMTX가 아니라 go2rtc를 쓴다. cctvgo-service가 자식 프로세스로 관리하는 쪽이 기존 구조와 맞다(빌더 결정).
- `cctvgo.bat`: 시작 시 정리 대상과 상태 점검에 `go2rtc.exe`를 넣는다. 방화벽 규칙 단계(4.5)를 추가한다. 다른 설치 폴더의 프로세스를 건드리지 않는 원칙(`processes.js`)을 유지한다.
- `make_package.bat`: `go2rtc.exe`를 넣는다. `run_single_stream.bat`과 HLS 관련 파일은 뺀다. FFmpeg는 남긴다. 새 주석은 ASCII로 쓴다(긴 한글 주석 줄을 cmd가 잘못 읽은 전례).
- cloudflared 터널 설정(ingress)은 바꾸지 않는다.
- 업데이트 안내: HLS 방식에서는 어디서든 보였지만, 새 방식은 일부 네트워크에서 외부 시청이 안 될 수 있다는 점을 배포 안내에 쓴다.

## 8. PC H.265 변환 시험 결과 (다음 작업의 근거)
- 번들 FFmpeg(N-119886, libx264 없는 LGPL 빌드)에 `h264_qsv`, `h264_amf`, `h264_nvenc`, `h264_mf`(Windows 내장)가 있다.
- **libx264(GPL)는 넣지 않는다.** GPL 의무(정확한 소스 제공, 재배포 제한 불가 등)와 특허 부담을 피한다.
- 변환 순서: 브라우저가 H.265 지원 → 원본 / 그래픽 하드웨어(qsv 등) → 실시간 / Windows 내장 소프트웨어(`h264_mf -hw_encoding 0`) → 1~2초 지연.
- 측정(2560x1440 H.265 → H.264 4Mbps, i5-1334U):
  - qsv: 실시간, CPU 3~7%, 메모리 약 290MB
  - mf: 화질은 qsv와 거의 같음, 1~2초 늦음, CPU 약 6%, 메모리 약 800MB(일정함). 저지연 설정(`ld_vbr`, `video_conference`)으로 바꿔도 체감 차이 없음. 메모리는 개발하며 줄인다.
- go2rtc에서 주의할 점:
  - 기본 h264 템플릿은 libx264라서 실패한다. qsv는 `ffmpeg.h264` 템플릿을 바꿔서 쓴다.
  - 임의 이름의 템플릿(`#video=h264mf`)은 동작하지 않아서, mf는 `exec:ffmpeg ... -f rtsp {output}`으로 지정해야 했다.
  - 변환에는 go2rtc 내부 RTSP(127.0.0.1)가 필요하다.
- Windows N 에디션에는 mf 변환기가 없을 수 있다(추측). 그 경우 안내한다.
