# 카메라 주소 찾기 (RTSP Finder) 설계

작성일: 2026-09-27 / 브랜치: `feature/rtsp-finder`

## 목적

사용자가 `cctv.txt`를 직접 편집하지 않고, CCTVGO 웹 UI에서 "카메라 주소 찾기"를 눌러 RTSP URL을 자동으로 찾고 `cctv.txt`에 반영할 수 있게 한다. ONVIF 미지원 구형 카메라를 포함한 모든 IP 카메라 사용자가 대상이다.

## 제약 (설계에 영향을 주는 전제)

- 설치형 제품이라 출시 후 코드/DB를 사용자에게 일괄 업데이트하기 어렵다. 그래서 커버리지를 처음부터 넓게 잡고, 필요 시 사용자가 데이터 파일 하나만 교체해 보강할 수 있게 한다.
- 실기 테스트 카메라는 2대뿐이다. ONVIF는 실기 검증이 제한되므로, 재검증과 폴백으로 "잘못된 결과를 내지 않는 것"을 보장하고, 실기 검증 여부는 별도로 기록한다.

## 범위

포함:
- 로컬 서브넷 카메라 후보 탐색 + IP 수동 입력
- 아이디/비밀번호로 RTSP URL 자동 탐색 (ONVIF 우선, 경로 후보 폴백)
- 자동 탐색 실패 시 수동 입력(IP/포트/경로) + 접속 테스트
- 실패 시 진단 정보 복사
- 결과 확인 후 `cctv.txt` 저장 (추가/교체, 백업)
- 외부 `rtsp-paths.json`으로 후보 보강

제외 (이번 범위 아님):
- 저장 후 스트림 자동 재시작 (저장 후 "cctvgo.bat을 다시 실행하세요" 안내만 표시)
- 서버에서 후보 DB 자동 다운로드
- 기본 비밀번호(1234) 변경 유도
- 녹화, H.265 대응, WebRTC

## 사용자 입력값

| 값 | 필수 | 비고 |
|---|---|---|
| 아이디/비밀번호 | 필수 | 자동으로 알 수 없음 |
| 카메라 IP | 선택 | 스캔으로 후보 표시, 안 잡히면 수동 입력 |
| 포트 | 불필요 | 554 우선, 8554/88 등 시도 (수동 입력 화면에서는 지정 가능) |
| 경로 | 불필요 | 이 기능이 찾는 값 (수동 입력 화면에서는 지정 가능) |
| 카메라 이름 | 선택 | 저장 시 입력 |

## 아키텍처

신규 모듈 `backend/finder/`, `server.js`에는 라우트 등록만 추가한다 (pkg 번들에 포함되도록 `require`로 로드).

| 파일 | 역할 |
|---|---|
| `scan.js` | 서브넷 계산, 포트 스캔(`net`), WS-Discovery(`dgram`, 보조: 제조사/모델 힌트) |
| `onvif.js` | ONVIF 유니캐스트 SOAP (`GetSystemDateAndTime`, `GetProfiles`, `GetStreamUri`), WS-Security 인증 |
| `rtsp-probe.js` | RTSP DESCRIBE 직접 전송, Basic/Digest 인증, 응답 코드/헤더 분류 |
| `paths.js` | 내장 경로 후보(제조사별 + OEM 공통 패턴, 약 100개) + 외부 `rtsp-paths.json` 병합 |
| `cctv-file.js` | `cctv.txt` 파싱/저장, 주석 헤더 보존, 백업, URL 인코딩 |
| `diagnostics.js` | 진단 정보 텍스트 생성 (비밀번호 제외) |
| `guard.js` | 사설 IP 검증, 동시 스캔 1개 제한, 요청 횟수 제한 |

### 접근 방식 선택 이유

- ffprobe는 미포함이며, 후보당 프로세스 실행은 느리고(수 초) 실패 원인 구분이 어렵다. RTSP DESCRIBE를 소켓으로 직접 보내면 응답 코드(200/401/404)로 원인을 정확히 구분하고 후보당 0.1~0.3초에 끝난다.
- ONVIF는 카메라가 URL을 직접 알려 주므로 경로 후보 DB에 없는 카메라도 찾을 수 있다. 업데이트가 어려운 설치형에서 커버리지 확보에 유리하다.
- 코덱/썸네일이 필요하면 기존 `cctvgo-ffmpeg.exe`를 성공한 URL 하나에만 사용한다(후속 확장).

## 탐색 순서 (`probe`)

`probe`는 방법을 순서대로 시도하는 구조로 만든다.

1. **ONVIF `GetStreamUri`**
   - 서비스 주소 후보 포트(기본 80, 8080, 2020, 8000, 8899)와 서비스 경로(`/onvif/device_service` 등)를 순서대로 시도. 각 시도 타임아웃 약 3초.
   - WS-Security 시계 오차는 `GetSystemDateAndTime`으로 시차를 계산해 보정.
   - 응답 XML은 네임스페이스 접두사에 의존하지 않고 파싱.
   - 응답에 포함된 주소가 요청 IP와 다르면(0.0.0.0, 내부 IP 등) 요청한 IP로 치환.
   - **얻은 URL은 반드시 RTSP DESCRIBE로 재검증**하고, 200일 때만 채택한다.
   - 프로파일이 여러 개면 메인/서브 스트림 후보로 함께 반환하고 사용자가 선택한다(기본은 첫 번째).
   - 어떤 예외/타임아웃/파싱 실패도 삼키고 다음 단계로 넘어간다.
2. **경로 후보 DESCRIBE**: 내장 + 외부 후보를 순서대로 시도하고 200이면 채택.
3. 모두 실패하면 `path_not_found`(또는 `unreachable`, `auth_failed`)와 진단 정보를 반환.

ONVIF 단계가 실패해도 결과는 2번 단계만 있는 경우와 같아야 한다(회귀 없음).

## 외부 `rtsp-paths.json`

설치 폴더(`cctv.txt`, `config.json`과 같은 위치)에 두는 선택 파일. pkg 실행 파일 안에 묻히지 않는다. 있으면 내장 값에 **합쳐서** 사용하고, 없거나 파싱에 실패하면 내장 값만 사용한다(로그만 남김).

```json
{
  "paths": ["/custom/path1", "/live/ch00_0"],
  "onvifPorts": [80, 8080],
  "onvifServicePaths": ["/onvif/device_service"]
}
```

용도: 문의로 제조사/경로를 알게 되었을 때, 새 항목이 담긴 파일을 사용자에게 전달해 폴더에 덮어쓰게 한다. 재빌드/재설치가 필요 없다. 이후 신규 패키지에는 내장 후보로 반영한다. ONVIF 로직 자체(코드)는 이 방식으로 고칠 수 없으므로, 값으로 분리 가능한 포트/서비스 경로만 데이터로 둔다.

## API

모두 기존 `authMiddleware`(세션 로그인)를 적용한다. 새 인증 방식은 만들지 않는다.

- `POST /api/finder/scan` — 서브넷 스캔. 응답: `[{ ip, port, vendor?, model? }]`
- `POST /api/finder/probe` — 입력 `{ ip, port?, username, password, path? }`. `path`가 있으면 그 경로만 시도(수동 입력/접속 테스트), 없으면 위 탐색 순서를 따른다. 응답: `{ status: 'found' | 'auth_failed' | 'path_not_found' | 'unreachable', candidates?: [{ url, source: 'onvif' | 'path', label? }], tried, diagnostics? }`
- `POST /api/finder/save` — 입력 `{ url, name, mode: 'append' | 'replace', replaceIndex? }`. 응답: `{ status, restartRequired: true }`

## 진단 정보

탐색 실패 시 응답에 `diagnostics` 텍스트를 포함하고, UI의 "진단 정보 복사" 버튼으로 복사할 수 있다. 내용:
- 카메라 IP, 열린 포트
- RTSP 응답 헤더 (`Server`, 401 응답의 `WWW-Authenticate` realm 등 제조사/모델 힌트)
- WS-Discovery/ONVIF 응답의 제조사/모델
- 시도한 경로 목록과 결과 코드
- **비밀번호는 포함하지 않는다.**

## 보안

- 대상 IP는 사설 대역(10.x, 172.16-31.x, 192.168.x)만 허용. 외부 IP와 호스트명은 거부. ONVIF 응답이 알려 주는 주소로 임의 접속하지 않고, 항상 요청한 IP를 사용한다.
- 스캔은 동시 1개, `probe`/`save`는 분당 횟수 제한.
- 비밀번호는 로그와 진단 정보에 기록하지 않는다.
- 스캔 범위는 서버 NIC의 서브넷(최대 /24)으로 한정.

## `cctv.txt` 저장 규칙

- 저장 전 `cctv.txt.bak` 생성.
- `#` 주석과 빈 줄은 그대로 보존, 카메라 줄만 추가/교체.
- 형식: `rtsp://아이디:비밀번호@IP:포트/경로, 이름`
- 아이디/비밀번호는 URL 인코딩 (`#`→`%23`, `$`→`%24`, `!`→`%21` 등, 기존 코드표와 동일).
- 이름의 콤마는 제거/치환(파서가 `,`로 분리하기 때문).
- 임시 파일에 쓴 뒤 rename하여 저장 실패 시 원본을 유지.

## 프론트엔드

- 신규 뷰 `frontend/src/views/CameraFinder.vue`, 라우트 `/finder`.
- `LiveCctv.vue`에는 진입 버튼만 추가 (기존 로직 변경 없음).
- 기본 흐름: 스캔 → 카메라 선택(또는 IP 수동 입력) → 아이디/비밀번호 → 자동 탐색(진행 표시) → 결과 확인(후보가 여러 개면 선택) → 이름 입력 → 저장 → 재시작 안내.
- 자동 탐색 실패 시:
  - 원인별 안내: 비밀번호 오류 / 경로 못 찾음 / 접속 불가.
  - "직접 입력" 화면: IP, 포트, 경로를 넣고 접속 테스트, 성공하면 저장.
  - "진단 정보 복사" 버튼.
  - "카메라 설명서에서 RTSP 주소를 확인하세요" 안내와 감지된 제조사 표시.

## 계정 잠금 방지

카메라는 로그인 실패가 일정 횟수를 넘으면 계정을 잠글 수 있다. 잠금 기준은 카메라마다 다르고 알 수 없으므로 절대 방지는 보장할 수 없고, 아래 장치로 위험을 최소화한다.

- **인증 실패 예산**: 카메라(IP)당 **인증 실패 최대 2회**. 아이디/비밀번호를 실어 보낸 요청이 401로 거절된 횟수를 ONVIF와 RTSP 단계를 합쳐서 센다. 예산을 소진하면 즉시 중단하고 안내한다. (인증 없이 보내는 첫 챌린지 요청은 실패로 세지 않는다.)
- **성향 감지**: 후보 시도 전에 존재하지 않는 경로(예: `/cctvgo-probe-test`)로 인증 요청을 한 번 보낸다.
  - 404 → 인증 통과 + 잘못된 경로에 404를 주는 카메라. 이후 후보를 계속 시도(인증 실패가 없으므로 예산 소모 없음). 이후 401이 나오면 비밀번호 오류로 확정하고 중단.
  - 401 → 비밀번호 오류이거나, 경로가 틀려도 401을 주는 카메라. 예산 1회 소모. 이후 가장 가능성 높은 후보(ONVIF 알림 URL 또는 감지된 제조사의 기본 경로) 1개를 시도하고, 다시 401이면 예산이 소진되어 중단한다.
  - 200 → 해당 경로 채택(정상 카메라는 이 경우 없음).
- **UI 재시도 누적 차단**: 실패 횟수는 서버가 IP별로 기억한다(메모리, 약 30분). 사용자가 화면에서 비밀번호를 바꿔 여러 번 재시도해도 합산하며, 예산 소진 후에는 대기 시간이 지나기 전까지 인증 요청을 거부하고 "카메라 잠금 방지를 위해 잠시 후 다시 시도하세요"라고 안내한다.
- **수동 입력 접속 테스트**도 같은 예산을 공유한다.
- 안내 문구에 "카메라 자체 웹페이지에서 로그인이 되는 아이디/비밀번호인지 먼저 확인하세요"를 포함한다.
- 비밀번호가 맞는 경우에는 인증 실패가 발생하지 않으므로 예산과 무관하다.

## 오류 처리

- `unreachable`: 포트 닫힘, 타임아웃(연결 1초, DESCRIBE 2초, ONVIF 3초).
- `auth_failed`: 인증 실패 예산 소진 또는 404 성향 카메라에서 401 발생. 비밀번호 확인 안내.
- `auth_locked`: 예산 소진 후 대기 중. 대기 시간과 사유 안내.
- `path_not_found`: 모든 후보가 404 → 직접 입력 안내.
- 경로가 틀려도 401을 주는 카메라에서 예산 내에 URL을 못 찾으면 "비밀번호 또는 경로 문제일 수 있음" 안내와 진단 정보, 직접 입력을 제공한다.
- ONVIF 단계의 모든 실패는 조용히 폴백. 단, ONVIF 인증 실패(SOAP Fault `NotAuthorized` 등)는 인증 실패 예산에 포함한다.

## 테스트

- `rtsp-probe`: 로컬 mock RTSP 서버(200/401/404, Basic/Digest)로 단위 테스트.
- `onvif`: ONVIF 명세 예시 응답으로 만든 mock 서버로 파싱, WS-Security 헤더 생성, 시계 오차 보정, 잘못된 IP 치환, 재검증 실패 시 폴백을 테스트.
- `paths`: 외부 `rtsp-paths.json` 병합, 파일 없음/파싱 오류 시 내장 값 사용.
- `cctv-file`: 주석 보존, 인코딩, append/replace, 백업 검증.
- `guard`: 사설/공인/호스트명 IP 판정, IP별 인증 실패 예산(2회 소진, 대기 중 거부, 대기 후 해제, UI 재시도 합산).
- 성향 감지: mock 서버 두 유형(없는 경로에 404 / 401)에서 인증 실패 횟수가 예산을 넘지 않는지 검증.
- 실제 카메라 2대(`192.168.219.100` Hikvision, `192.168.219.194` onvif 경로 사용 장비)로 수동 검증. 각 카메라가 ONVIF에 응답하는지 확인해 결과를 기록하고, 응답하지 않으면 ONVIF는 mock 테스트까지만 검증된 **미검증 기능**으로 명시한다.

## 열린 항목

- 2대 카메라의 ONVIF 응답 여부(구현 초기에 `GetSystemDateAndTime`으로 확인).
- `&` 포함 주소(예: Dahua `?channel=1&subtype=0`)가 `start_ffmpeg.bat`/`run_single_stream.bat`을 통과하는지: 2026-09-27 mock 카메라(`backend/tests/helpers/amp-path-check.js`, 임시 패키지 폴더에서 실제 스크립트 실행)로 확인 — 수정 전 FAIL(`start_ffmpeg.bat`이 URL을 `cmd /c` 인자로 넘겨 `&` 뒤가 별도 명령으로 잘림), 수정 후 두 형식(기존 형식, `&` 포함 형식) 모두 PASS. 수정: URL을 명령줄 인자 대신 환경 변수 `STREAM_URL`로 전달(`start_ffmpeg.bat`이 `start` 직전에 설정, `run_single_stream.bat`이 읽음. 나머지 인자는 `%1`~`%3`으로 이동).
- 2대 카메라가 "없는 경로"에 404/401 중 어느 쪽을 주는지(실기 검증). 두 유형 모두 mock 서버로 테스트한다.
